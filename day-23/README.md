> **给后端工程师的一句话**：RAG 召回质量的天花板，不在向量库、不在大模型，而在**怎么切文档**。块切歪了，检索就召回"半句话"或"一锅粥"，再强的模型也救不回来。分块（chunking）本质就是个**字符串切分函数**——你天天写，今天只是给它加上"沿语义边界切"的约束。先玩可视化看三种切法的差别，再自己写一把。

## 📖 学习内容（约 30 分钟）

### 1. 为何要分块（why chunk）

整篇文档不能直接塞进模型，原因有三：① **上下文窗口有限**——再大的窗口也装不下整个知识库；② **检索要精准**——把"猫的习性"和"咖啡因"切成两块，提问咖啡时才不会捞到猫；③ **成本与噪声**——块越小越聚焦，但太碎又丢上下文。所以分块是个**字符串切分函数**：`chunks = split(doc)`，目标是切出"够小能进上下文、够大保完整语义"的片段。

后端类比：和你把一条大日志按 trace 切段、把大文件分片上传一样——切的粒度决定后续每一步好不好处理。

### 2. 固定窗口 + overlap（fixed size + overlap）

最简单：每 N 个字符切一刀。问题是**会拦腰斩断句子**——"猫不像狗那样依赖主人 | ，但也会蹭腿"。补救是**重叠（overlap）**：相邻块共享尾部 K 个字符，步长 `step = size - overlap`。跨界的句子在两块里各有一半，检索哪块都能召回完整意思。

```
固定:  [0,50) [50,100) [100,150)           # 50 字硬切，接缝处断句
重叠:  [0,50) [40,90) [80,130)             # overlap=10，相邻块共享 10 字接缝
```

代价：overlap 越大召回越稳，但块数变多、存储与重复内容增加。典型取 size 的 10%~20%。

### 3. 递归按分隔符（recursive split）

固定大小不看内容，递归则**优先沿自然边界切**：先按段落 `\n\n` 切，太长再按句号 `。` 切，还长按逗号 `，`，实在不行才按字符切。这就是 LangChain 默认的 `RecursiveCharacterTextSplitter`——"从粗到细，能不打断就不打断"。`practice.py` 用 4 级分隔符 `["\n\n","。","，",""]` 复刻了它的核心。

```
分隔符优先级：段落(\n\n) → 句子(。) → 子句(，) → 字符()
逻辑：先用最粗的切；某块仍超 size，就换下一级更细的再切（递归降级）
```

效果：块沿句号/段落对齐，语义完整度远好于硬切——`practice.py` 里递归块就是"一段=一块"。

### 4. 语义分块（semantic chunking）

更聪明：不靠标点，靠**意思**。把文本按句切，逐句算 embedding，**相邻句相似度骤降处**就是主题切换点，在那里切。`practice.py` 末尾正用 `nomic-embed-text` 算相邻块余弦——跨主题（猫→咖啡→RAG）处相似度明显更低，那正是该切的缝。语义分块就是把这条信号自动化：相似度低于阈值=换主题=下刀。

代价：要先嵌入全文，慢且贵；递归对结构化文本已够好。**默认递归，文档主题混杂时再上语义。**

### 5. chunk 大小权衡（trade-off）

| 块太小（如 100 字） | 块太大（如 2000 字） |
|---|---|
| ✅ 检索精准、聚焦 | ✅ 上下文完整、少切断 |
| ❌ 丢失上下文、召回半句 | ❌ 噪声多、塞不下、检索糊 |

没有标准答案：QA 短问答用小块（200~500 字）+ overlap；长文摘要用大块。**先用递归 + size 500 + overlap 50 起步，再按召回效果调**——这就是今天的核心权衡。
