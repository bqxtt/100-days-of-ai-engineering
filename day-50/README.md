# Day 50-51 — Agent 评估：如何系统化测试 Agent 的能力

> **阶段**：Phase 4 · AI Agent 开发（**2 天合并** · 接 Day42 实战「焊好的 Agent」）
> **主题**：Agent 跑通不等于跑好——多步轨迹里随时会用错工具、绕弯路、给出不靠谱的最终答案。今天造一个迷你 eval harness（评估框架），用 4 指标 + LLM 裁判，把「它真的好用吗」从拍脑袋变成成绩单
> **预计耗时**：约 2 天 × 1 小时（Day50 跑通+读懂 4 指标，Day51 加用例/换裁判模型+复盘）
> **给后端工程师的一句话**：评估 Agent = 给 Agent 写**集成测试**（integration test）。难点在它不是「一个函数一个返回值」，而是一条**多步轨迹**（trajectory）：先想、再调工具、看结果、再想……任一步歪了最终都崩。所以不能只断言最后一个返回值，要测「成功率（对不对）+ 步数效率（绕没绕路）+ 工具选对率（契约对不对）+ 最终质量（写得好不好）」四件事。前三件机器自动判，最后一件请第二个模型当裁判（LLM-as-judge）。改完 prompt 就跑整套——掉分=回归（regression）。

## 📖 学习内容（约 25 分钟）

### 0. 为什么 Agent 难测：轨迹（trajectory），不是返回值
普通函数测试：输入→断言输出，一锤定音。Agent 是 `想→调工具→观察→再想` 的循环，**中间任一步走歪，最后都不可信**：用错工具、多绕三步、工具调对了但答案抄错。只看最后一句对不对 = 漏掉一路上的坑。所以评估对象是整条**轨迹**：步数、工具序列、每步观察、最终答案，都要测。
> 后端类比：单测（unit test）测一个纯函数；Agent 像一条跨服务调用链，得做**集成测试**，还要看链路上每一跳。

### 1. 四个指标：覆盖「对不对 / 快不快 / 对不对路 / 好不好」
| 指标 | 中文 | 测什么 | 自动判定方式 |
|---|---|---|---|
| Task Success Rate | 任务成功率 | 最终答对没有 | 期望值是否出现在答案里 |
| Step Efficiency | 步数效率 | 有没有绕弯路 | 实际步数 vs 应有步数 |
| Tool Correctness | 工具选对率 | 走对路了没 | 调齐了契约里该用的工具？ |
| Output Quality | 最终质量 | 写得清不清楚 | LLM-as-judge 打 1-5 分 |
前三个机器秒判、不花钱；只有「质量」是主观的，交给裁判模型。**别只看成功率**——它 67% 也可能工具全对、就一步抄错，分维度才看得出病灶。

### 2. 三种方法：测试集 + LLM-as-judge + 轨迹检查
- **测试集（eval set）** = 用例表：每条 `目标 + 期望答案 + 期望工具`，就是断言。改 prompt 跑一遍，对比分数。
- **LLM-as-judge** = 第二个模型当裁判：客观分测不了「答案写得好不好」，让模型按 rubric 打分（代替人工评审）。
- **轨迹检查（trajectory check）** = 翻工具序列：成功率达标但绕了 5 步？工具序列一看就知道哪歪了。

### 3. 后端对照：集成测试 / 契约测试 / 回归
| 评估手段 | 你熟的后端概念 |
|---|---|
| 测试集跑用例 | 集成测试（integration test）套件 |
| 期望工具序列 | 契约测试（contract test）：该调的服务调了吗 |
| 每次改 prompt 跑全套对比 | 回归测试（regression）：分掉了=引入回归 |
| LLM-judge 质量分 | 人工评审的自动化代餐 |
框架不神秘——把「断言」从 `assert x==1` 换成「成功率/工具序列/裁判分」，CI 思路一模一样。

### 4. 为什么要框架而非手测：可回归、可对比
手动跑一次「看着对」=不可复现。框架把成绩单数字化：改模型/改工具/改 prompt → 跑 → 成功率 60%→85% 才敢上线，掉了立刻拦。**评估是 Agent 的护栏，没它你不知道改动是进步还是退步。**

## 🤔 思考题（边做边想）

1. 第 3 条用例工具选对（mul→add）、答案却错。如果只测「成功率」会漏诊；只测「工具选对率」又会误判通过。**为什么单一指标都不够**？
2. LLM-judge 自己也是个会犯错的模型，让它给 Agent 答案打分，怎么知道裁判靠谱？（提示：给裁判也准备「标准答案」抽查校准）
3. 现在用例硬编码 3 条。扩到 50 条真任务、每改一次 prompt 全跑一遍——这跟你 CI 里的回归套件差在哪？该多久跑一次、谁来更新期望值？
